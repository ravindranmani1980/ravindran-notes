Networking compared

VPC networks, VPCs and VNets side by side: subnets, routing, NAT, peering, hybrid links, load balancers, DNS and private access in Google Cloud, AWS and Azure.

The three clouds build networks from the same ideas (private address space, subnets, routes, gateways, load balancers, DNS), but they draw the boundaries differently. The biggest difference: a Google Cloud VPC network is global, while AWS VPCs and Azure virtual networks are regional. Most other differences follow from that.

The guides behind each column: Google Cloud, AWS and Azure. For protection (firewalls, WAF, DDoS), see Network protection compared.

What it means in practice. In Google Cloud, a multi-region application can live in one network with one set of firewall rules, and VMs in different regions talk over internal IPs with no peering. In AWS and Azure, the same design needs a network per region, connected by peering or a transit service. In AWS, put a subnet in each Availability Zone you use; in Google Cloud and Azure, one subnet already covers every zone in its region.

Design tips that carry across

  • Plan address space once, for every cloud and on-premises. Overlapping ranges are the one networking mistake that's really expensive to fix later. These notes use 10.10.0.0/16 (Azure), 10.20.0.0/16 (AWS) and 10.30.0.0/16 (Google Cloud) for that reason.
  • Hub and spoke everywhere. Shared services (DNS, egress, inspection, hybrid links) in a hub; workloads in spokes. Shared VPC, Transit Gateway and Virtual WAN are each cloud's way of doing it.
  • Private by default. No public IPs on servers, outbound through managed NAT, platform services through private endpoints. Each cloud has a policy to enforce it.
  • Turn on flow logs and keep a connectivity-test habit. All three have a tool that answers "is it the firewall?" in a minute.
